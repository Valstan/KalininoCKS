## Гейты и деплой

- Гейты перед PR (если трогался код): `corepack pnpm lint && corepack pnpm typecheck && corepack pnpm build` (build требует локальный Postgres — Payload лезет в БД на пререндере).
- PR-гейт в CI — job **`gates`** (`.github/workflows/ci.yml`): сканер секретов gitleaks по всей истории, затем lint / typecheck / сборка против эфемерного Postgres. Фильтров по путям у него намеренно нет: проверка обязательна в защите `main`, а `paths:`-фильтр подвесил бы навсегда PR, не трогающий эти пути. Известные исторические срабатывания сканера — в `.gitleaks.toml`, с объяснением каждого.
- Мерж в `main` → **авто-деплой на прод** (`deploy-prod.yml`). ⚠️ У воркфлоу `paths-ignore`: `docs/**`, `**.md`, `.github/**`, `.claude/**` — эти файлы деплой **не** триггерят (поэтому brain-интеграция и доки не гоняют пересборку).
- Миграции схемы Payload — **вручную ДО деплоя** через `apply-migration.yml` (workflow_dispatch, migration-guard #017), затем деплой через dispatch.

## Git и совместная работа нескольких агентов

- `main` защищён логически: ветка → коммит → push → PR → **squash merge**. Прямой push в `main`, force-push и `reset --hard` запрещены.
- Один агент — одна задача — своя ветка; при одновременной работе нескольких пишущих агентов — отдельный `git worktree`. Не запускай двух пишущих агентов в одном рабочем дереве.
- Перед правкой проверяй `git status`. **Незнакомые изменения считай чужими:** не удаляй, не форматируй попутно, не включай в свой коммит и не прячь в stash.
- Не переключай ветку в рабочем дереве, которое может использовать другой агент.
- Объявляй границы файлов/задачи в описании PR. Пересеклись границы — второй агент ждёт merge первого и ребейзит свою ветку до начала правок.
- Один PR — одна задача. Коммиты — Conventional Commits.
- После обрыва сначала восстанавливай фактическое состояние из Git/PR, не повторяй действия по памяти.

Git — механизм координации между моделями; **чат одной модели не источник истины для другой**. Долговечные решения живут в документации/ADR, состояние незавершённой работы — в `docs/SESSION_HANDOFF.md`, история — в коммитах и PR, межпроектная связь — в `mailbox/`.

## 📬 Mailbox check — ДО любой другой работы (ADR-0001 v3)

Асимметричные mailbox'ы: каждая сторона пишет только в свой репо.

| Направление | Кто пишет | Где |
|---|---|---|
| `brain → Калинино ЦКС` | brain | локально: `../brain_matrica/mailboxes/KalininoCKS/from-brain/*.md`; на GitHub: тот же путь в `brain_matrica` |
| `Калинино ЦКС → brain` | мы | **`mailbox/to-brain/*.md`** в этом репо (через PR) |

Сканить только корень `from-brain/` (не `DRAFTS/`, не `ARCHIVE/`) **в двух read-only источниках**: в локальной копии `../brain_matrica/` и на GitHub (`main`, через API/веб без clone/fetch/pull). Объединять письма по относительному пути. Если письмо есть в обоих источниках и содержимое различается, сравнить историю изменения именно этого файла: незакоммиченная локальная версия — более свежий кандидат, иначе ориентироваться на последний коммит файла локально и на GitHub. При неоднозначности прочитать обе версии и явно доложить конфликт; ничего не перезаписывать и не синхронизировать. Версия репозитория в целом не определяет свежесть отдельного mailbox.

Compliance: `mandate`→MUST, `recommend`→SHOULD (отказ обосновать письмом), `suggest`→MAY. Письма без `compliance`: `directive`→MUST, `idea`→SHOULD.

Формат исходящего письма `mailbox/to-brain/YYYY-MM-DD-slug.md`:

```yaml
---
from: KalininoCKS
to: brain
date: YYYY-MM-DD
topic: ...
kind: idea | question | feedback | report
compliance: suggest | recommend | mandate   # для kind=idea
urgency: low | normal | high
---
```

## 📚 Библиотека Мозга — при непонятной грабле (рефлекс #014)

Наступил на непонятное поведение (пустые логи, «зелёный» ответ без содержимого, магический таймаут, странность вендора) — **до собственного расследования** грепни библиотеку по симптому:

```bash
grep -in "<симптом>" ../brain_matrica/cross-project-ideas/GOTCHAS.md
```

Там 30+ находок ровно нашего стека (Next + Payload + PostgreSQL + nginx), собранных соседними проектами экосистемы: G136 (аналитика молча режет визиты нового домена), G223/G224 (публикация и идемпотентность ingest), G231 (сверка схемы при ручных зеркальных миграциях), G234 (keep-alive против прокси), G237 (информер Метрики отдаёт валидную картинку с нулями). Дешевле прочитать чужой разбор, чем повторить чужой инцидент.

Библиотека read-only. Нашёл **переносимую** находку у себя — оформи её письмом в `mailbox/to-brain/`, Мозг внесёт в библиотеку сам. Правило симметрично: письмо Мозга может устареть, а библиотека — свежее (так было с punycode-советом G136), поэтому при расхождении письма и библиотеки ориентируйся на дату амендмента и доложи расхождение.

## Начало и завершение работы

В начале работы:

1. Сначала синхронизируй **только этот** репозиторий (`git fetch`, затем безопасный fast-forward при чистом дереве).
2. Не выполняй никаких синхронизирующих или изменяющих Git-команд в `../brain_matrica/` и других соседних репозиториях.
3. Прочитай и сопоставь входящие письма Мозга из локального и GitHub-источника (см. §Mailbox check), выбери более свежую версию каждого письма и доложи сводку.
4. Прочитай `docs/SESSION_HANDOFF.md`, проверь `git status` и последние коммиты.

В конце значимой работы обнови `docs/SESSION_HANDOFF.md`, сохрани изменения через PR, оставь **свой** репозиторий синхронизированным и чистым, а чужие локальные репозитории — нетронутыми.

Подробные **исполняемые памятки** лежат в `.claude/commands/`: [`start.md`](.claude/commands/start.md), [`close_session.md`](.claude/commands/close_session.md), [`obriv.md`](.claude/commands/obriv.md). Несмотря на имя каталога, их workflow применим к любому агенту. Правило перевода в vendor-neutral: строку `allowed-tools:` игнорируй; `/команда` = «выполни шаги этого файла»; указание вида `AskUserQuestion: «…»` = «задай вопрос и дождись явного ответа пользователя». **Форма любая, шаг обязателен** — предохранитель не снимается из-за отсутствия конкретного инструмента.

## 🛡 Публичный репозиторий — recon-поверхность

Репозиторий **публичный** с 17.08.2026 ([D-030](../brain_matrica/docs/DECISIONS.md)). Правило ниже сформулировано через **свойство содержимого**, а не через канал публикации, и это принципиально: прежний предохранитель звучал «не публиковать на витрине» — он пережил смену канала и перестал защищать, **не выглядя нарушенным** ([#189](../brain_matrica/cross-project-ideas/ideas/189-a-ban-written-about-one-channel-does-not-survive-the-channel-change.md)). Пока репозиторий был приватным, разница между «на сайте» и «в документах репозитория» имела смысл; 17 августа она исчезла.

> **Опубликованным считается любой текст, который может увидеть человек без доступа к площадке.** Отслеживаемый файл, лог прогона Actions, тело PR или issue и комментарий к ним, текст аннотации `::error::`, артефакт прогона, релиз-нота, публичная страница. Список — **примеры, а не исчерпание**: появился новый канал вывода — он подпадает под правило по умолчанию, без отдельной поправки.

Определение намеренно дано через свойство «видно снаружи», а не через перечень носителей: перечень уже пришлось расширять дважды за одну сессию (файлы → логи прогонов), и каждый раз новый канал не выглядел нарушением.

Не кладём в отслеживаемые файлы **вообще**:

- IP-литералы и технические хостнеймы серверов (в том числе вида `<hex>.vps.<хостер>`), имя хостера;
- обозначения и имена боксов, состав их жильцов, колокацию сервисов, объём ресурсов и его дефицит («малый бокс», «мало RAM»);
- порты прод-сервисов и внешние SSH-порты;
- пути в файловой системе сервера (`/etc/…`, `/home/…`), имена env-файлов, vhost'ов, бэкапов и сертификатов;
- имена системных и SSH-пользователей, имена и алиасы SSH-ключей;
- внутренние URL: шлюзы, служебные эндпоинты, адреса соседних проектов.

Куда класть вместо репозитория: **`secrets` GitHub** (не `vars` — почему, ниже), env-файл на самом сервере, приватная карточка проекта в `brain_matrica`. Имена переменных публиковать можно и нужно — запрещены **значения**: по именам в `deploy-prod.yml` состав требуемого окружения восстанавливается, а по пустым строкам в `web/.env.example` — что вообще должно быть задано.

**Проверять грепом по содержимому, а не по именам файлов и не по памяти.** «У меня такого нет» без показанного прогона не считается: у соседа нашлось в четырёх местах при написанном и соблюдаемом предохранителе.

**Логи прогонов Actions: у публичного репозитория они публичны, и греп по файлам их не видит.** Четыре способа туда попасть, все встречались у нас:

- **`vars` вместо `secrets` — главное.** Раннер печатает блок `env:` шага в лог **с раскрытыми значениями**; маскируется только то, что заведено как `secrets`. Проверено на нашем же прогоне: в одном блоке `SSH_PRIVATE_KEY: ***`, а рядом хостнейм и SSH-порт открытым текстом. Значит **recon-чувствительное значение обязано быть `secrets`**, и перенос его в `vars` ничего не закрывает;
- подстановка `${{ … }}` прямо в тело `run:` — выражение раскрывается ДО запуска, и скрипт печатается в лог уже с подставленным значением. Обращаться `$VAR` из `env:`, тогда в лог уйдёт литерал `$VAR`. **Это защищает только тело скрипта, но не блок `env:`** — сама по себе мера недостаточна;
- `echo` фактов, полученных с сервера (`hostname`, пути, вывод `id`) — в файле репозитория при этом чисто;
- дамп журнала сервиса при падении. `journalctl` по умолчанию печатает «дата ХОСТНЕЙМ юнит[pid]: текст», то есть имя машины в каждой строке, а `systemctl status` тянет тот же хвост. Брать `journalctl … -o cat` и `systemctl status … -n 0`, а вывод дополнительно пропускать через редактирование: текст ошибки подключения может нести целую строку `DATABASE_URI` (см. шаг «On failure» в `deploy-prod.yml`).

Оговорка про очень короткие значения: маскируется каждое вхождение секрета в логе, поэтому значение вроде `22` замажет и все даты. Внешний SSH-порт у нас поэтому осознанно оставлен в `vars` — 22 универсален и recon-ценности не добавляет, а нечитаемый лог стоит дороже.

**Функционально необходимое значение** (юнит не стартует без `EnvironmentFile=`, workflow не найдёт сервер без хоста) сначала выносим в `secrets`/env. Если вынести нельзя, не сломав механизм, — оставляем и **фиксируем как осознанный остаток**: в списке ниже, комментарием в самом файле и в отчёте. Молчать нельзя: следующий аудит грепом не отличит принятый остаток от свежего нарушения.

|---|---|---|
| `deploy/kalinino.service` | имя системного пользователя, рабочий каталог, путь env-файла, зависимость от локального `postgresql.service` (колокация БД), лимит памяти | юнит копируется на сервер **дословно**; плейсхолдер разошёлся бы с установленным, а расхождение репозитория с продом — отдельный класс аварий |

**Честная граница.** Вычистка **ничего не отзывает**: всё, что уже лежало в отслеживаемом файле, ушло в историю, форки и кэши и остаётся публичным. Это гигиена на будущее, а не устранение, — лечит смена адреса или ротация доступа, а не правка текста ([#060](../brain_matrica/cross-project-ideas/ideas/060-leaked-secret-public-repo-response.md)). Поэтому:

- ❌ **не переписываем историю** (`main` защищён, force-push запрещён, и это всё равно ничего не отзывает);
- ❌ **не правим уже сделанные записи** — разделы «Сделано» прошлых сессий в `docs/SESSION_HANDOFF.md`, отправленные письма `mailbox/to-brain/`, старые отчёты, — даже если сегодняшнее правило их содержимого уже не разрешило бы. Это записи о том, что было; переписывать их нечестно. Пишем аккуратно **новые**.

Запрет — про **записи**, а не про файл целиком: шапка, «Текущая нитка» и «Следующий шаг» в `docs/SESSION_HANDOFF.md` обновляются штатно (§Начало и завершение работы, `/close_session`) — это текущее состояние, а не история.

## 🧰 Текст — файлом, а не внутри командной строки

Мандат владельца [D-046](../brain_matrica/docs/DECISIONS.md):

> **Не сочиняй текст внутри командной строки. Никогда.**
> Пиши содержимое инструментом записи файлов, а команде отдавай **путь** — один ASCII-токен, который переживает все слои экранирования, тогда как содержимое не встречает парсер ни разу.

Дело не в heredoc: он не убирает **ни одного** слоя. Текст внутри команды проходит до четырёх парсеров — кавычки аргумента инструмента → локальный шелл (на Windows их два с несовместимым синтаксисом, G190) → удалённый шелл при `ssh` (G30) → кодовая страница консоли (G191). Автор держит в голове один слой, а платит за четыре, и отказ выглядит как ошибка в коде или данных, а не в доставке текста.

| Задача | Вместо | Правильно |
|---|---|---|
| Скрипт / патч / конфиг | `cat <<'EOF' > f.py` | записать файл инструментом записи |
| Commit message | `-m` с переносами, `@'…'@` | файл → `git commit -F msg.txt` |
| PR / issue body | `--body "…"` | файл → `gh pr create --body-file body.md` |
| SQL на проде | `psql -c "…"` | файл → `scp` → `psql -f q.sql` |
| HTTP-тело | heredoc в `curl` | файл → `curl --data-binary @body.json` |
| Файл на удалённый хост | heredoc через `ssh` | `scp`, либо `base64 -w0 f \| ssh host 'base64 -d > /path'` |

**Триггер:** увидел в собственной команде перенос строки, backtick, `$`, кавычку или не-ASCII — остановись и перепиши через файл, **не экранируй**.

**Чего правило НЕ отменяет:** однострочные ASCII-команды без кавычек внутри; короткие ASCII `-m`/`psql -c`. Порог — появление любого символа из триггера.

**Пятый слой, наш собственный (28.08):** на Windows к четырём парсерам добавляется **подмена содержимого, похожего на путь**. Git Bash считает unix-подобный аргумент путём и переписывает его (MSYS path conversion): `gh variable set SOME_PATH --body /etc/<app>/<app>.env` записал `C:/Program Files/Git/etc/…`. Команда однострочная, чистый ASCII, без кавычек и `$` — под исключения выше подпадает, а значение исказилось молча. Поэтому **абсолютный unix-путь в аргументе — тоже триггер**. Передавай значение через stdin: `gh secret set NAME < f` — подстановки нет вовсе. Не пиши `printf %s $(cat f) | …`: незакавыченная подстановка разобьёт значение по пробелам и раскроет globs, то есть испортит его так же молча. Если нужен именно аргумент — `MSYS_NO_PATHCONV=1` и обязательные кавычки.

⚠️ **Heredoc'и, уже лежащие в коммитнутых файлах, — не нарушение и переписывать их ЗАПРЕЩЕНО** во исполнение этого правила. `<<'REMOTE'` и `<<CFG` в `deploy-prod.yml` и `apply-migration.yml` (и в любых будущих файлах) — части сохранённых скриптов, написанных инструментом записи: текст там не проходит ни одного лишнего парсера. Правило касается текста, который агент **сочиняет в момент выполнения команды**. Попытка «выровнять их под мандат» через `scp` + внешний скрипт молча теряет позиционные аргументы и ломает ручное применение миграций — единственный путь менять схему прода.
