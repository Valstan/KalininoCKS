# Ручные миграции: сверять схему по колонкам, а не «что добавил в PR»

## Что случилось

При импорте из ВК (Калинино, 04.08) миграция `20260804_123500` писалась **вручную** (зеркальный `.ts`+`.sql`, как принято в кластере — локального Postgres нет, `migrate:create` недоступен). В неё вошла коллекция `categories` + `posts.category_id`, но **не вошли** колонки `source_url` / `_posts_v.version_source_url` для поля `sourceUrl`, добавленного в тот же PR в `Posts.ts`. Миграция применилась, код задеплоился, и все 29 запросов ingest упали `500: column _posts_v.version_source_url does not exist` (Payload в versions-таблице требует `version_<поле>` для каждого поля коллекции с версиями).

Фикс — ALTER вручную на проде + досинхронизация файлов миграции (PR #13). Потеряно ~15 минут и один цикл «деплой → падение → логи → фикс».

## Инсайт (переносимый для всего кластера)

Когда миграция пишется руками, легко учесть только то, что **помнишь** из своих правок. Надёжнее сверяться с полным дифом:

1. **Перед apply** прогнать по чеклисту «каждое новое/изменённое поле коллекции → колонка в основной таблице + `version_*` в `_v`-таблице (+ FK/индекс для relationship)». Источник истины — diff `payload-types.ts` (или `generate:types` до/после правок коллекций): он ничего не знает о БД, но показывает полный состав полей.
2. Для relationship: `<field>_id` в таблице коллекции, `version_<field>_id` в версиях, FK `<table>_<field>_id_<reftable>_id_fk` + индекс (паттерн см. в initial-миграциях кластера).
3. Идеал — генерировать миграцию на боксе с живым Postgres (`migrate:create`), а зеркальный `.sql` извлекать из `up()`, как делали с initial. Пока локальный PG не чинится, чеклист п.1 — замена.

## Связь с G-реестром

Кандидат в GOTCHAS: «ручная зеркальная миграция теряет колонки versions-таблиц» — если Мозг сочтёт достойным реестра.
